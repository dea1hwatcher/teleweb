# План фиксов TeleWEB — по итогам код-ревью от 03.11.2026

База ревью: ветка `dev`, коммит `a939763` (v0.1.6). `go vet` чист, кросс-сборки и все
тесты зелёные — план ниже про корректность, а не про сборку.

Модель ветвей: ревью-находки живут в Go-ядре, которое входит во все четыре ветки
(`dev`, `android`, `win`, `linux`). Ветки не мержатся, а черри-пикаются, поэтому
каждый этап заканчивается прогоном и раскаткой фиксов по веткам (см. раздел 6).

## Этап 0 — Синхронизация dev ↔ android (фундамент, делать первым)

**Проблема:** `dev` отстал от релизных веток: нет `initMemoryTuning`
(`debug.SetGCPercent(50)` — тюнинг GC под Android RAM), нет `routeCacheTTL = 6h`
и `routeCacheFresh()` (переоценка маршрутов, коммит `ab1cc74`), нет
`src/webui_test.go`. Любой фикс, сделанный сейчас на dev и черри-пикнутый в
релизные ветки, «откатит» эти наработки при обратной синхронизации.

**Решение:**
1. Черри-пик в `dev` из `origin/android`:
   - блок `initMemoryTuning` + вызов в `main()`;
   - блок `routeCacheTTL` / `routeCacheFresh` + использование в `dialTelegramWS`;
   - `src/webui_test.go`;
   - удаление мёртвого `WsPool.Close()` (в android уже удалён — см. Этап 4.1).
2. После переноса прогнать `git diff origin/dev origin/android -- src/` и убедиться,
   что расхождение = только desktop-уникальный код dev.
3. Зафиксировать в `docs/RELEASING.md` правило: перед релизом из `android` сверять
   `git diff android dev -- src/main.go src/ws_pool.go` на потерянные блоки.

**Критерий готовности:** `go test ./...` зелёный, диф dev↔android содержит только
desktop-фичи, `WsPool.Close` удалён.

## Этап 1 — Безопасность трафика (P0)

### 1.1. Закрыть SOCKS5-вектор «открытого прокси» через подделку DC 203

**Проблема:** `socks.go:130` спекулятивно пропускает любой IP на портах
443/80/8443/5222. Подделав в 64-байтном init DC-индекс = 203, локальное
приложение получает raw-TCP-туннель на произвольный адрес (`handleCDN203`
диалит `orig.Addr()` напрямую, `main.go:3170-3193`) — ломается контракт
«Telegram DC endpoints only» (`socks.go:18`).

**Файлы:** `src/main.go` (`serveConn`, `handleCDN203`), `src/socks.go`, тесты.

**Решение:**
1. Прямой TCP-passthrough в `handleCDN203` разрешить только если
   `isCDN203IP(orig.Addr())` — т.е. назначение само является легитимным
   CDN203-эндпоинтом. Для остальных случаев при `dc == 203` — закрывать
   соединение с логом `refusing forged CDN203 for non-Telegram dst`.
2. Путь через Cloudflare Worker оставить как есть: `dialCFWorker` ходит на
   фиксированный `cdn203IP` по allowlist воркера, произвольные адреса туда
   не попадают.
3. Спекулятивный allow в `socks.go` сузить: пропускать произвольный IP на
   «Telegram-портах» только когда адрес реально в агрегатах Telegram
   (`isTelegramEndpoint`/`isTelegramEndpointV6`); для доменных запросов —
   только `isTelegramDomain`.

**Тесты:**
- forged init (dc=203) → dst 8.8.8.8:443 → соединение закрыто, туннеля нет;
- тот же forged init → dst 91.105.192.100:443 → passthrough разрешён;
- SOCKS CONNECT на произвольный не-Telegram IP:80 → REP=2 (есть частично,
  расширить на 443).

**Риск:** легитимные сценарии, где клиент просит CDN203-диапазон, не затронуты —
проверяется агрегатом. Мedia-клиенты с «тестовыми» диапазонами — тоже.

### 1.2. Оградить `learnDC` от загрязнения

**Проблема:** `learnDC` (`main.go:1675`) вызывается для любого распарсенного
`orig` до диспетчеризации 203 (`main.go:3014`). Произвольные IP оседают в
`dc-learned.json` и могут занять весь лимит 256, вытесняя реальные
media-эндпоинты.

**Решение:** в начале `learnDC` — reject для адресов вне агрегатов Telegram
(новый хелпер `isTelegramAggregate(ip)`, общий для v4/v6, поверх
`telegramParsedSubnets` + `telegramV6Subnets`).

**Тест:** `learnDC("8.8.8.8", 203, false)` → запись не появляется;
`learnDC("149.154.175.52", 2, true)` → появляется.

## Этап 2 — Надёжность трафика (P1)

### 2.1. IPv6-перенаправление: не глотать ошибку iptables

**Проблема:** `setupRules` (`main.go:1726`) игнорирует ошибку `ip6tables`.
При неудаче IPv6-трафик Telegram (2001:b88::/32) уходит напрямую, мимо WSS —
без единой строчки в логе.

**Решение:** обрабатывать ошибку: `logf("redirect: IPv6 rules failed: %v —
Telegram IPv6 will bypass WSS", err)`. В `rulesHealthy` не проверять (чтобы
watchdog не реставрил правила на роутах без ip6tables), но в статус/лог
поставить одноразовое предупреждение при первом отказе и рестарте демона.

### 2.2. Убрать блокировку `appCacheMu` на время `discoverApps`

**Проблема:** `installedApps` (`main.go:1315`) держит мьютекс во время тяжёлого
скана (сотни subprocess'ов `pm`/`cmd` + открытие APK). На холодном старте
`writeStatus` (тик 5 c) и watchdog висят на этой же блокировке.

**Решение:**
1. Реструктурировать: быстрая проверка кэша под локом → скан вне лока →
   запись результата под локом. Единственность скана — через отдельный
   `discoverMu` (второй вызывающий ждёт и берёт готовый результат).
2. Заодно: `findPackageAPK(pkg)` в `discoverApps` вызывается 2–3 раза на пакет
   (isTelegramAPK + иконки) — закешировать путь в локальной переменной и
   переиспользовать.

**Риск:** гонка «два скана подряд» исключается `discoverMu`; поведение
`discoverActiveTelegramClients` (watchdog) не меняется.

### 2.3. Ограничить параллельность POST в H2-media мосте

**Проблема:** `cf_h2.go` на каждый MTProto-пакет порождает горутину+POST,
`http.Transport` без `MaxConnsPerHost`. Заливка файла → сотни параллельных
H2-стримов → 429/троттлинг всего моста.

**Решение:** семафор `h2InFlight chan struct{}` (cap 16) на время жизни POST:
acquire перед `go func` с учётом `bridgeCtx`, release после отправки reply
в `replyCh`. На переполнении — пакет ждёт семафора (не дропается).

**Тест:** стресc-тест: 100 пакетов подряд → максимум 16 одновременных
`h2PostPacket` (счётчик внутри теста).

### 2.4. Fail-fast при потерянном POST в H2-media

**Проблема:** провалившийся POST занимает seq-слот «пустым» ответом
(`h2ReplySequencer` пропускает `nil`). Если сервер всё-таки ответил позже —
ответ потерян, а серверный CTR-поток уже продвинулся → все последующие
ответы клиент расшифрует в мусор, media-сессия тихо умирает.

**Решение:** в reply-writer'е: первый `r.data == nil` → `bridgeCancel()` +
лог «H2 media bridge: request seq=N lost; closing session to avoid CTR
desync». Клиент MTProto переподключится сам.

**Риск:** на флапающих сетях мост станет рвать сессию чаще, чем сейчас
(сейчас — «живой труп»). Это правильнее: честный reconnect лучше тихой
порчи потока.

### 2.5. Считать download-байты в H2 с length-префиксом

`cf_h2.go:311` — заменить `len(body)` на `len(encoded)`, чтобы статистика
H2-пути совпадала с WSS-путём (там считаются кадры целиком).

## Этап 3 — Рефакторинг и дедупликация (P2)

### 3.1. Свести Status-маппинг к одному конструктору

Три копии полей: `currentStatus()`, `status()` (merge из status.json),
default-литерал `status()` (`main.go:2299-2430`, ~90 строк × 3). Сделать
`func buildStatus() Status` c общими полями (флаги из файлов, tailLog и т.д.),
а три вызова — только переопределяют живые метрики/оверрайды. Новое поле
добавляется в одном месте.

### 3.2. Один источник списка IPv6-агрегатов

Сейчас `telegramV6` (`main.go:1368`, для iptables) и
`telegramParsedSubnetsV6` (`socks.go:146`, для проверки) дублируют одни и те
же CIDR. Сделать единственный `telegramV6CIDRs []string` + производные
(parsed-префиксы и строковый список) через `init()`-функции, как сделано для
v4 (`telegramSubnets` → `telegramV4` → `telegramParsedSubnets`).

### 3.3. Оживить (или убрать) проход по /proc/net/tcp6

**Проблема:** `parseProcNetTCPIP` парсит только 8-hex IPv4; для tcp6
(32 hex) всегда false → цикл в `scanActiveTelegramSockets` по tcp6 —
мёртвый. Клиенты с чисто-IPv6 сокетами не обнаруживаются.

**Решение (реализовать, объём маленький):** парсер 32-hex адресов
(включая IPv4-mapped → `Unmap()`), проверка через `isTelegramEndpointV6`
(уже есть в socks.go — переиспользовать).

**Тест:** fixture-строка tcp6 с 2001:67c:4e8::ENDPOINT → uid найден;
IPv4-mapped запись → найден через v4-агрегаты.

### 3.4. Общий каркас pipeWSTunnel / pipeTCPToTCP

Оба дублируют: `closeBoth` через `sync.Once`, idle-ticker c 5-минутным
таймаутом, циклы копирования со счётчиками. Вынести хелпер
`runIdleWatchdog(stopIdle <-chan struct{}, lastActivity *atomic.Int64, onIdle func())`
и использовать в обоих. Логику копирования не трогать (пути разные:
framer vs raw) — риск регресса не оправдан.

### 3.5. Дедуплицировать логику фреймера в cf_h2

`tryBridgeH2Media` повторяет `mtprotoPacketFramer.feed` (append+XORKeyStream,
shrink буфера) с расхождениями. Добавить метод
`(*mtprotoPacketFramer).popPackets() [][]byte` — «верни все завершённые
пакеты (plain, включая length-префикс)», использовать в обоих местах.
Поведение WSS-пути не меняется (метод — обёртка над существующим циклом).

### 3.6. mediaForIP — оставить как bootstrap, добавить комментарий

Хардкод-список media-IP дублирует знания learned-кэша. Убрать не можем
(bootstrap до первого обучения), но пометить это в комментарии, чтобы список
не расширяли руками без необходимости.

## Осознанно НЕ меняем (найдено, но исправление нецелесообразно)

- **GOMEMLIMIT** — комментарий в `initMemoryTuning` фиксирует регрессию
  (GC death spiral при clamp 48 MB). Оставляем `SetGCPercent(50)`.
- **O_APPEND-логирование и ротация в `logf`** — работает корректно, `clearlogs`
  безопасен именно благодаря O_APPEND.
- **`workerCooldowns` без чистки** — фактически bounded (ключи = известные
  хосты×DC), утечки нет.
- **`serverListening()`-проба на Windows** — создаёт пустые коннекты, но EOF
  нейтрален и не счётится как fail; переделывать на netstat ради косметики —
  лишний риск.
- **`serve()` accept-loop `continue`** — busy-loop возможен только при
  закрытом listener, который никогда не закрывается до выхода процесса.
- **Алокации в `readFrame`** (`make([]byte, n)` на кадр до 16 MB) — GC-давление
  на media терпимо; пулировать кадры — отдельная оптимизация с риском
  use-after-free в фрагментации, не для этого прохода.
- **`routeCacheTTL`-механика** — переносится как есть из android (Этап 0),
  дизайн менять не нужно.

## Порядок работ и «definition of done»

1. **Этап 0** — синхронизация ветвей (полдня): cherry-picks + диф-проверка + тесты.
2. **Этап 1** — P0 security (полдня): 1.1 + 1.2 + юнит-тесты, черри-пик во все ветки.
3. **Этап 2** — P1 надёжность (день): 2.1–2.5, черри-пик, ручной smoke H2.
4. **Этап 3** — P2 рефакторинг (день): 3.1–3.5, полный прогон тестов.
5. **Этап 4** — P3 чистка (час): один коммит «chore: drop dead code».
6. **Этап 5** — валидация перед релизом: кросс-сборки + on-device smoke.
7. **Этап 6** — раскатка: android → тег → релиз; win/linux → attach.

Каждый этап = отдельный коммит(ы) на dev с последующим черри-пиком; в конце —
релиз v0.1.7 по `docs/RELEASING.md` (14 ассетов), обновление `update.json` на
`master` через CI.
