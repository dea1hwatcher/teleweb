# Диагностика нагрузки и памяти

Когда Telegram работает, а телефон греется, нужно отличить две поломки:
сборщик мусора не успевает за аллокациями, или демон устроил шторм из
соединений. Оба случая выглядят как высокий CPU, но починка разная.

## Что читать в status

`tgws status` (или `cat /data/adb/teleweb/status.json`) отдаёт живой срез
процесса. Поля для этого случая:

| поле | смысл |
|---|---|
| `gcNum` | сколько циклов GC прошло с запуска |
| `gcCpuPercent` | доля доступного процессу CPU (GOMAXPROCS × время), ушедшая на сборку |
| `gcPauseAvgMs` | средняя остановка мира на цикл (оценка вверх по бакетам метрик) |
| `heapLiveBytes` | живая куча Go, то что сборщик обязан обойти |
| `memNowBytes` | RSS всего процесса, включая не-кучу |
| `uptime`, `active`, `ws`, `fail` | аптайм, открытые соединения, WSS-рукопожатия, сбои |

Снимки пишутся каждые 5 секунд, поэтому сравнивай два снимка с интервалом
~60 секунд, а не одно число:

- **GC-спираль**: `gcCpuPercent` десятки процентов, `heapLiveBytes` не
  падает, прирост `gcNum` за минуту исчисляется десятками, `ws`/`fail`
  при этом спокойные. Лечится аллокациями в горячем пути и лимитами
  буферов, а не уменьшением `GOMEMLIMIT` — урезанный лимит спираль только
  усиливает.
- **Шторм соединений**: `gcCpuPercent` в пределах пары процентов, зато
  быстро растут `fail` и `ws`, в логе повторяются «Happy Eyeballs winner»
  и переборы роутов.
- **Не Go-память**: `memNowBytes` заметно больше `heapLiveBytes` —
  смотрим на драйверы и сторонние библиотеки, а не на сборщик.

## pprof по TELEWEB_PPROF

Профили включают переменной окружения; без неё бинарник ничего не слушает.
Адрес обязан быть loopback — эндпоинт отдаёт дампы кучи, наружу его выпускать
нельзя. Значение `0.0.0.0:6060` демон игнорирует и пишет об этом в лог.

Десктоп (Windows/Linux):

```sh
TELEWEB_PPROF=127.0.0.1:6060 tgws run          # PowerShell: $env:TELEWEB_PPROF=...
curl -o cpu.pb.gz "http://127.0.0.1:6060/debug/pprof/profile?seconds=30"
go tool pprof -top cpu.pb.gz
curl -o heap.pb.gz "http://127.0.0.1:6060/debug/pprof/heap"
```

Android — демон запускается из service.sh без нашего окружения, поэтому
для профилирования его нужно перезапустить вручную (на время этого шага
трафик Telegram идёт напрямую):

```sh
su
/data/adb/modules/teleweb/bin/tgws stop
TELEWEB_DIR=/data/adb/teleweb TELEWEB_PPROF=127.0.0.1:6060 \
  /data/adb/modules/teleweb/bin/tgws serve &
curl -o /data/local/tmp/cpu.pb.gz \
  "http://127.0.0.1:6060/debug/pprof/profile?seconds=30"
```

Дальше `/data/local/tmp/cpu.pb.gz` забирается на компьютер и разбирается тем
же `go tool pprof -top`. Счётчики в `status` дешевле, так что начинаем с них,
а pprof подключаем, когда они не объясняют нагрузку.

## Что присылать с репортом

1. `tgws status` дважды с интервалом минуты.
2. `tail -n 60 /data/adb/teleweb/tgws.log`.
3. `top -H -b -n1 -p $(cat /data/adb/teleweb/tgws.pid)` — видно, какие потоки
   едят CPU (`gc` против `dial`/`crypto`).
4. Версию модуля из `module.prop`.
